# Ascension — Disposable PostgreSQL owner-run map acceptance

**Date:** 2026-11-02  
**Status:** CI-only PostgreSQL validation; not a production DB or login acceptance.

## Purpose
The prior `gateway/owned-map-session.test.mjs` used a mocked `pool.query`. This separate job verifies the **real** PostgreSQL 16 query and JSONB storage semantics with the staged owner-scoped map reader, a saved world generated by the recovered v4 map generator, and the published display-contract validator.

## How to reproduce safely
Run GitHub Actions `Phaser 4 visual lab checks` → `Disposable PostgreSQL owner-run acceptance`. The job creates a throwaway `postgres:16-alpine` service and the database `ascension_map_test`, applies `gateway/migrations/001_player_runs.sql`, writes only manufactured player runs, and drops its table at completion.

The test intentionally **refuses** to run unless `PGHOST=127.0.0.1` and `PGDATABASE=ascension_map_test`. It never uses NXCore, any production database URL, or AVCC credentials.

## Assertions
- PostgreSQL stores and returns actual JSONB state from the recovered `AFTERLIFE` world-map generator.
- The player-run reader's SQL binds `owner_subject`; the `alice` identity receives only the newest `alice` run, even when another player's run is newer.
- Absent owners, invalid identities and unauthorized capability checks fail closed.
- The response passes the Phaser map-view validator but excludes private fields, unrevealed map data, NPC/spawn data, RNG seed and queued cutscenes.
- A revision outside JavaScript's safe integer range fails rather than rounding.
- The run reader does **not** update stored state or revision.

## Production blockers remain
1. ACOS PR #126, the deployed `ascension-auth` image, and the live account handoff must be reconciled. The reviewed PR remains draft and unmerged, despite the health endpoint being live.
2. The actual service uses the native `ascension_avcc_session` cookie and `https://ascension-auth.aerovista.us`. The older `aa_cards_session` example is not live. The `/api/game/map` endpoint remains absent.
3. Explicit real capability-grant registration and live account/identity lifecycle acceptance are required.
4. A managed PostgreSQL deployment, migration/backup plan and least-privilege application role must be approved separately.
5. Canonical movement, turn, cutscene, RNG and delayed consequence parity must pass before persistent play is offered.

**Do not interpret a successful CI PostgreSQL test as permission to apply a migration to a production database or to publish a player-login button.**
